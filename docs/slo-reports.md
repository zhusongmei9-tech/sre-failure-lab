# SLI、SLO 与演练报告

这一阶段把“故障后恢复了”变成可解释的测量结果。它不把模拟控制器动作当成真实容器恢复，
也不把一小段流量当成一个月的可用性承诺。

## 口径先定清楚

- **SLI**：成功请求数 / 完成的商品 HTTP 请求总数；仅 2xx 算成功。
- **SLO**：本实验默认 99%，是教学参数，不是生产 SLA 或合同承诺。
- 429、404、422、500、503 都进入失败数，避免靠主动拒绝请求把成功率美化。
- 健康探测、文档、指标抓取不在这个分母中；网络失败没有到达服务器，必须另看客户端报告。
- 业务原有的“5xx 错误率”与这个 SLI 不同，两者要分别展示，不能混称。
- 错误预算 = 完成请求数 × (1 - 目标)。消耗比例 = 失败数 / 错误预算，允许超过 100%。
- 预算剩余最低显示 0%，超过部分另记录 `error_budget_overrun_ratio`，不能抹去超支。
- 零请求时成功率和预算是 **无数据**，不是 100% 成功或 0% 错误。

例如 1000 次请求，990 次 200、5 次 429、5 次 503：成功率 99%，10 次失败恰好耗尽预算。
若 100 次中只有 90 次 200，则成功率 90%，预算消耗 1000%、超支 900%、剩余 0%。
这些是按请求数计算，不是“允许停机几分钟”。

## 故障 → 指标 → 告警 → 排查 → 恢复 → 预期输出

### 1. 故障

按 `cpu-lab.md` 增加 CPU 运算并给予并发流量，可能出现 429；或按 `runbooks.md` 注入随机 500。
保持同一组实验的 RPS、并发、缓存状态和 CPU 配额不变。所有控制接口需要实验令牌。

### 2. 指标

```promql
# 5 分钟成功率；分母为 0 时没有序列，而不是假装健康
lab:slo_success_ratio:5m

# 99% 目标下，5 分钟与 1 小时的错误预算燃烧速率
lab:slo_burn_rate:5m
lab:slo_burn_rate:1h

# 单独确认 429 是否成为主要失败来源
sum(rate(lab_http_requests_total{job="api",status_code="429"}[5m]))
```

`slo.yml` 新增 recording rules 和告警，需由 Prometheus 配置加载。规则中的目标固定为 99%，
Python 报告的 target 可配置，但两者不会自动同步；改变目标时必须同步规则中的 0.01，
并重跑规则测试，不要让报告与看板各用一个目标。

### 3. 告警

`LabSLOFastBurn` 要求：

- 5m 和 1h 两个窗口的燃烧速率同时大于 14.4；
- 5m 至少 100 次请求，1h 至少 1000 次请求；
- 连续满足 2 分钟才进入 firing。

这里的 14.4 是教学阈值，不宣称完整实现了生产多级错误预算告警策略。低流量可能没有
告警，不代表没有故障；仍需结合原有 API DOWN、缓存失败和延迟告警。刚启动时窗口
包含的历史不足，务必注明实际观察时长。告警仅在 Prometheus 中展示，没有自动通知收件人。

规则测试覆盖无流量、正常请求、429 预算消耗及低流量抑制。可在有 promtool 的环境运行：

```bash
cd monitoring/prometheus
promtool check rules slo.yml
promtool test rules slo.test.yml
```

本轮编写和静态检查不等于 Prometheus 已上线；是否实际运行 promtool 以交付验证记录为准。

### 4. 排查

1. 核对时间范围、计数器是否重置和是否更换 API 实例。
2. 按状态码拆分失败，区分 CPU 保护产生的 429、输入错误和 5xx。
3. 比较服务端请求耗时与客户端 P95。服务器直方图分位数是估算，不是原始样本的精确分位数。
4. 对照操作事件时间线，确认是人为演练、模拟控制器事件还是实际 API 请求变化。
5. 无数据先检查 target 和流量，不要把缺失数据补成 0 或 100%。

### 5. 恢复

清除应用故障、停止压力，确认后续请求恢复。清除故障不会擦除已经消耗的预算，
Prometheus 滚动窗口也不会瞬间归零。要对比恢复前后，使用同样长度的独立时间段。
当前进程报告基于提供的真实计数器快照，不自动执行 Redis 恢复、重启或流量切换。

### 6. 预期输出与报告

报告包含：生成时间、验证范围、统计区间、状态码计数、成功率、目标、预算消耗/剩余/超支、
P95 值及其测量口径、最近最多 200 条操作事件。

当没有请求时，JSON 中应出现：

```json
{"has_data": false, "success_ratio": null, "target_met": null,
 "error_budget_remaining_ratio": null, "p95_seconds": null}
```

Markdown 应显示“无数据”“未测量”，而非绿色成功。`validation_scope` 可为 simulation、
component 或 full_stack；它是调用者提供的测量范围声明，不会自动证明全栈已验证。
当前业务组件计数与模拟控制器并存时使用 component，不能据此宣称真实自愈/发布成功。

## 导出安全边界

报告只接受白名单字段，不复制环境变量、令牌、请求头、异常堆栈或任意详情。事件导出仅包含
合规 ID、动作和时间，不导出 raw details。Markdown 转义 HTML、竖线和换行。
报告不是长期审计系统：事件是有界内存记录，重启会丢失；进程计数器也会重置。
不要将不同进程的累计快照直接相减后称为同一个窗口。

开发接口：`summarize_slo(status_counts, ...)` 计算指标，`build_report(snapshot, events, ...)`
组装 JSON 安全数据，`render_markdown(report)` 生成可读报告。输入错误抛出 ValueError，
调用方应返回明确 4xx，不把它当成服务成功结果。
