# 带持续流量的真实验收

在 137 的专用实验栈中运行以下命令。它会真实注入故障、停止容器并切换版本，约需 3–4 分钟。不要与另一轮演练同时执行。

```bash
cd /opt/sre-failure-lab
python3 -u scripts/accept_traffic.py --rps 20 --workers 8
```

前提：真实自愈服务已启动，当前发布处于 idle，缓存降级已开启，活动槽无注入故障；本机已有 0.3.0 和 0.3.1 两个演练镜像。脚本只支持这两个版本，最终恢复起始版本，并通过真实发布和回滚验证保留另一版本作为回滚副本。

## 流程

持续请求 Nginx 业务入口的商品 1、2、3，依次执行：

1. 30 秒正常基线。
2. 15 秒延迟注入（每次请求增加 300ms）。
3. 20 秒有界 CPU 工作。超出应用并发限制时允许返回 429，并计入失败请求。
4. 停止 Redis，检查 BYPASS 降级和真实自愈。
5. 停止活动 API，记录用户收到的错误，检查真实自愈。
6. 正常发布另一版本，观察 20 秒，再手动回滚。
7. 候选切流后注入 100% 500，验证自动回滚、关联事件及发布命令非零退出码。
8. 验证并恢复保留的回滚副本。
9. 30 秒最终恢复窗口，检查真实业务与监控数据。

正常阶段要求实际收到请求，且完整落在阶段内的请求没有非 2xx。故障阶段有独立的状态码范围与恢复检查，故障阶段返回错误不会被包装成全程零错误。CPU 阶段还要求观察到实际计算计数增长。

## 流量与统计口径

默认目标 20 请求/秒、8 个工作线程，上限 50 请求/秒、32 个线程。发生器按线程节奏发送、超时为 3 秒；慢请求导致吞吐下降时不追赶积压，因此目标 RPS 不等于实际 RPS，也不是容量极限测试。工作阶段最长 600 秒，退出后执行清理。

每条请求按发出时刻归属阶段，保留完成阶段和跨阶段标记。跨阶段请求计入原阶段总数与延迟；稳定阶段的错误门槛只检查完整落在该阶段内的请求，避免把下一阶段刚开始的故障错误算作上一阶段基线失败。报告同时保留两种计数。

阶段 P50/P95/P99 由该阶段全部请求延迟按最近秩计算，包含失败请求，不是成功请求专属延迟；不会把多个窗口 P95 取平均冒充总体 P95。

客户端记录还包含 Nginx 返回的 502/504 与连接失败。应用自身的 `lab_http_requests_total` 无法记录没到达应用的请求，因此入口停机影响以客户端原始请求为准，不能只看应用 5xx 比例。

发生器运行在 137 上，主机 CPU 包含发生器及其他进程的开销。API 进程 CPU 和容器 CPU 独立记录。修复后的自愈控制器将商品 429 识别为过载，不因此重启；其他实际故障仍可能触发重启并提前清除进程内故障，需对照故障状态快照及事件分析。

## 输出与复查

每轮独立保存到 `runtime/traffic-<UTC时间>/`，不覆盖历史运行：

- `report.json`：阶段结果、吞吐、状态码、P50/P95/P99、版本、验证失败及最终健康状态。
- `requests.jsonl`：每次真实请求的时间、状态码、缓存结果、版本、槽和耗时。
- `metrics.jsonl`：约每 5 秒采集的主机/进程/容器指标、采集器状态、实际告警和应用故障状态。
- `events.jsonl`：本轮实际发布、自愈事件。

报告不保存认证令牌。采集缺失与 NaN 不会补成零。短故障可能在告警 `for` 条件满足前恢复，不能据此认定告警规则失效；规则另由 `promtool test rules` 覆盖。

外部客户端也可单独发送有限流量，不操作容器或注入故障：

```bash
python3 loadgen/main.py --base-url http://172.16.58.137:18000 \
  --rps 10 --workers 4 --duration 60 --report-interval 10
```

每轮结束查看 `report.json` 的 `status`、`validation_failures`、`cleanup_errors` 与 `final_health`；脚本以非零退出表示失败，即使已安全恢复业务也不会改写为测试通过。
