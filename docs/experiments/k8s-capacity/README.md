# Kubernetes 商品查询容量实测

2026-11-20，在两台 ARM64 Linux 虚机上测试。135 运行 k6 v1.3.0（2 vCPU、约 3.5 GiB 内存），137 运行 K3s、业务和监控（2 vCPU、约 4.5 GiB 内存）。k6 通过只监听 135 回环地址的 SSH 隧道访问 137 上的容量实验 ClusterIP。延迟包含客户端、隧道、Service、API 与 Redis 的开销。[复现步骤](../../from-zero/05-capacity.md)

每个 API Pod 的 CPU 配额为 250m、内存上限为 192 MiB，独立 Redis 的 CPU 配额为 100m、内存上限为 64 MiB。实验使用同一应用镜像，固定工作负载的副本数。混合场景在三个有效商品之间轮换，先确认三个商品均有缓存命中，再开始计时。默认 TTL 为 60 秒，过期后会产生少量 MISS。商品的原始数据来自应用内的只读字典。[应用与看板的源码提交](https://github.com/zhusongmei9-tech/sre-failure-lab/commit/6ef4d9f9cb704975c2a1fe99ea6890bbe3706e11)

| ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 1 | 80 | 80.002 | 48,001 / 48,001 | 0 | 7 ms | 38 ms | 是 |
| 1 | 120 | 119.962 | 71,977 / 71,977 | 23 | 42 ms | 67 ms | 否 |
| 2 | 120 | 120.002 | 72,001 / 72,001 | 0 | 6 ms | 30 ms | 是 |

单副本在 80 请求/秒持续十分钟时达标。[80 请求/秒的监控窗口](one-lower-metrics.json)

单副本在三十秒时通过了 120 请求/秒。运行十分钟后，32 个虚拟用户一度全部占用，k6 记录了 23 次漏发。已发出的查询全部成功，客户端 P95 也在 100 ms 门槛内。双副本运行相同到达率，持续十分钟达到约定的全部门槛。120 请求/秒是双副本在这个实验配置中已经验证的持续吞吐下界。

### 哪个环节值得先调

下面是稳态内部窗口的采样均值。双副本时两个 Pod 平均分别处理 71.24、48.76 请求/秒。两个实例各有 250m CPU 上限，合计可用的 API CPU 配额也随副本数增加。

| 120 请求/秒时的服务端观测 | 1 个 API Pod | 2 个 API Pod |
| --- | ---: | ---: |
| 每个 API Pod 的平均 CPU 用量 | 197.4m | 125.5m、91.8m |
| 每个 API Pod 的平均 CPU 限流时间 | 128.2 ms/s | 3.2、0.4 ms/s |
| API 端观察的 Redis GET P95，其窗口采样均值 | 4.23 ms | 1.01 ms |
| 整台双核节点平均空闲 CPU | 1.42 核 | 1.39 核 |

单副本时整机仍有 CPU 余量，API 容器受配额限流的时间却显著增加。可以优先用单副本重复实验，只调整 API CPU 配额，核对尾延迟、漏发及限流时间如何变化。这里的 Redis 延迟包含 API 进程等待及重新获得调度的时间。仅凭这组数据还无法单独归因于 Redis 执行或服务端 CPU。

## 热点与冷启动

额外做了两档 2 副本、40 请求/秒、各 25 秒的烟测。热点商品共 1,001 次正确响应，全部 HIT，P95 为 8 ms。冷启动静默等待 65 秒，最开始的三个商品各返回一次 MISS，随后 997 次 HIT，1,000 次查询全部正确，P95 为 9 ms。此结果验证了从冷到热的读取过程。应用仅有三个商品，持续大量不同商品回源需要另设工作负载。

## 如何复核

运行的镜像构建标识为 `capacity`，使用 32 个预分配虚拟用户，每次迭代只查询一次商品。压测客户端的分子是正确的 2xx 商品响应，分母是实际发起数。另外检查漏发、计划到达数、请求完成数，并分别记录 429、超时等错误。99.9% 正确率和 P95 ≤100 ms 是本次实验门槛。

137 使用 K3s `v1.37.2+k3s1` 与 containerd `2.3.7-k3s1`。Pod 状态中记录的 API 镜像 ID 是 `sha256:331e6519442ac30136634cbc723025ab743473a13df45516e53ba687a505cf16`，Redis 镜像 ID 是 `sha256:eab78b9649d5ca8b91192621c91136c9c1465a81338fb686fbc02bac4dd851ae`。

[客户端原始报告](client-runs.json)保存每档的目标、计数、分位数与所有检查结果。前两轮短阶梯及双副本稳态使用了开发时的驱动快照，后续热冷烟测及单副本稳态使用已发布的驱动。两者的请求路径、流量模型、并发参数和验收门槛一致；后者增强了输入检查并增加 5xx 单独计数。原始报告保留各自实际采集的字段。

[单副本面板数据](one-steady-metrics.json)和[双副本面板数据](two-steady-metrics.json)来自 137 的 Kubernetes Prometheus，按 10 秒步长查询已部署看板的 16 条表达式。为让 1–2 分钟的滑动窗口只包含相应负载，取各次稳态开始两分钟后至结束前的区间。k6 和 Prometheus 记录各自虚机时钟；实验期间 135 的 UTC 时间比 137 快约一分钟，图表窗口按 137 时钟选取。

137 在线且 Prometheus 仍保留本次数据时，按第一章建立 3000 端口的 SSH 隧道，即可在浏览器回看[本次压测时段的 Grafana](http://127.0.0.1:3000/d/sre-k8s-capacity?from=1795170055000&to=1795172195000&var-namespace=sre-capacity-lab)。仓库中的 JSON 保留历史采样，方便在监控数据轮转后复查。
