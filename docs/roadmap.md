# SRE 故障演练实验室项目规划与当前进度

更新日期：2026-11-13。

项目目标是让一位 SRE intern 能够演示和解释三个能力：故障可自愈，CPU、内存、磁盘等资源可观测，部署过程可控制且版本可回滚。目前已经完成业务与故障演练基础；资源监控、自愈控制器和版本发布属于下一阶段规划，尚未实现。

## 当前验证状态

2026-11-12 的本地验证包含 16 项应用测试、6 组告警场景，以及真实 Redis、FastAPI、Prometheus 原生进程联调。基线/降级对比每种模式执行 30 次请求：Redis 故障下基线全部返回 503，降级模式全部返回 200；P95 均约 200ms，降级增加 30 次数据源读取。

这些结果来自 macOS 原生进程，数据源是内存字典，不代表真实数据库承载能力。Linux 虚拟机连接曾超时，尚未完成 Linux Docker 构建、Compose 全栈部署及 Grafana 浏览器显示验收。详情见 validation.md 和 experiments/native-comparison.json。

## 下一阶段一 资源可观测

目标：当业务变慢时，能通过同一时间轴判断是否与计算、内存、磁盘或网络有关。

| 资源 | 计划观察的指标 | 计划设计的实验 |
| --- | --- | --- |
| CPU | 虚拟机 CPU 使用率、负载、容器 CPU 使用和限流 | 可调计算量接口，比较不同计算量与 CPU 配额下的吞吐和 P95 |
| 内存 | 主机可用内存、容器内存用量与上限、OOM 事件 | 在有内存上限的独立实验容器中逐步增加占用 |
| 磁盘 | 容量、inode、读写速率和延迟 | 向专用实验目录限量写入，观察告警，停止写入并清理实验文件 |
| 网络 | 主机和容器吞吐、错误与连接情况 | 对比正常流量、较高流量与业务错误 |

实施候选：主机指标采集器、容器指标采集器接入已有 Prometheus，再扩展 Grafana 看板。具体工具、权限和挂载方式应在确认 Linux 发行版及容器环境后确定。

验收：资源变化能与业务变化对应；停止实验后能验证回落；不将“CPU 高”直接当成“业务故障”。

## 下一阶段二 受控自愈

目标流程：检测异常 → 连续失败确认 → 执行限定恢复动作 → 验证业务恢复 → 记录事件。

| 场景 | 计划采取的动作 | 验证方式 |
| --- | --- | --- |
| API 进程退出 | 自动重启服务 | 验证进程与商品接口均恢复 |
| API 进程存在但持续不健康 | 根据服务探测结果受控重启 | 比较重启前后业务探测结果 |
| Redis 故障 | 保持业务降级，尝试恢复缓存依赖 | 验证依赖恢复、请求重新使用缓存 |
| 持续无法恢复 | 停止重复修复并告警 | 验证达到重试上限后不再重启 |

自愈控制器需要连续失败阈值、冷却时间、有限重试、动作白名单和事件日志。容器运行时的进程重启机制与业务健康驱动的修复应分别展示。

暂定事件记录字段：事件 ID、服务、发现时间、症状、恢复动作、尝试次数、动作结果、恢复验证时间。单次事件记录发现与恢复耗时，多次事件后再统计平均值。

故障注入的定时结束只是清理机制；需要通过“故障不会自行消失，控制器仍能发现并修复”的场景证明自愈。

## 下一阶段三 可控发布与回滚

目标流程：选择明确版本 → 启动候选服务 → 就绪检查 → 业务冒烟测试 → 切换流量 → 观察 → 保留或回滚。

准备三个演示版本：v1 正常版本、v2 正常变更版本、v3-bad 故障版本。响应头或状态接口暴露版本号，每次发布记录镜像版本与前后状态。

两种实施路线：

- 简单更新：替换容器，验证失败后恢复上一镜像；实现较小，但可能出现服务中断。
- 蓝绿发布：保留新旧两套服务，通过入口代理切换流量；更容易演示切换和回滚，但需要额外资源。

优先考虑蓝绿发布，实施前确认虚拟机资源足够。旧版本在观察期内保留，失败时切回；首次部署没有旧版本时，应明确报告失败，不能宣称已回滚。发布操作应有互斥机制，避免同时发布。

当前商品业务为只读样例，先验证无数据库迁移的服务版本回滚。数据库结构回滚属于后续独立问题。

验收：候选版本未通过检查不接流量；切换后出错能回滚；操作记录能说明哪个版本何时接管；可执行手动回滚。

## 最后整合运维控制台

控制台规划为四个区域：服务与版本状态、资源与业务监控、故障演练操作、发布及自愈事件。当前尚未实现这个独立控制台，现有入口为 CLI 与 /docs。

先完成并验证后端操作与状态，再接界面。界面中的每个按钮都应有真实执行结果与事件记录。

## 推荐实现顺序

1. 完成现有项目的 Linux Compose 部署验收，记录虚拟机 CPU、内存、磁盘配置。
2. 接入主机和容器资源指标，完成 CPU 压力实验。
3. 添加受控自愈控制器，验证进程退出和依赖故障。
4. 添加版本号、候选版本探测和发布记录。
5. 实现蓝绿切换、观察期与自动回滚。
6. 整合控制台，补齐故障场景与复盘材料。

## 最终演示的三个故事

1. 制造 CPU 压力 → 资源与业务延迟变化 → 告警 → 解除压力并验证恢复。
2. 停止 Redis → 业务自动降级 → 控制器恢复依赖 → 自动恢复缓存使用。
3. 发布故障版本 → 检测到业务异常 → 自动回滚 → 旧版本重新接管。

项目展示重点是判断依据、恢复证据和工程取舍，而不只是工具数量。
